## 二、原理：出站链路改动前后对比

### 改动前（上游默认行为）

```
客户端 → Worker(WS 入站, 解出目标 host:port)
  → 出站连接:
     ① 直连:  Worker TCP → 目标 host:port
     ② 反代:  Worker TCP → {colo}.SsSs.nEt 的 DNS TXT 解析出的反代IP:443
              （第三方社区域名，首包携带目标信息由反代侧代答）
     直连失败 → 反代；反代失败 → 兜底直连
```

**问题**：第三方域名族稳定性不可控（DNS TXT 查询失败、域名被墙、反代节点失效都是 `scriptThrewException` 的直接来源）；出站 fetch 无超时 → 卡满 30s CPU → `exceededResources`。

### 改动后（auto 模式，新默认）

```
客户端 → Worker(WS 入站)
  → 出站连接（无手填 ProxyIP 时）:
     官方地址池(10 IP) → Fisher-Yates 打乱 → 分批并发竞速(TCP:443)
     → 首个连通者胜出（复用既有 Promise.any 竞速机制）
     → 全部失败 → 按 兜底 开关回落 connectDirect(原始目标)
  → manual(env.PROXYIP) / region(env.出站模式=region + path wk) 行为与旧版一致
```

**关键语义**：这 10 个官方 IP 属于 Cloudflare anycast 边缘段（162.158.0.0/15、172.64.0.0/13），Worker → CF 边缘的 TCP:443 连接与旧"反代"是同一种网络内部路径，只是把候选来源从"不可控的第三方域名"换成"内置官方地址"。与 byJoey/cfnew v3.0 同源方案（15.3k★，同平台 30 天 0 错误基线）。**CF 任播特性下同一地址在不同位置落到不同机房，因此无需按地区挑 IP——这也是 cfnew v3.0 删除地区探测的依据。**

**超时原理**：Worker 单请求 CPU 上限 30s，任何一个无超时的出站 fetch 卡住都会拖满配额。`AbortSignal.timeout` 给每个出站调用确定上限，失败被快速暴露后进入**既有** fallback 链（竞速兜底/直连兜底）——失败快速化反而提高最终成功率。

## 三、用量增量分析（对照计费维度）

| 维度 | 增量 | 机制与估算 |
|---|---|---|
| **Workers 请求数** | **+0** | 每客户端请求仍计 1 次；拦截与官方直连不产生新请求。计费请求数不变 |
| **子请求 subrequests** | **显著负增量** | ① 反代出站不再做第三方域名 DNS TXT 解析 + 域名连接（每次反代连接省 1-2 个子请求）；② bot 请求 404 短路（原 1+ 伪装页出站 → 0）；③ 超时砍掉卡死长尾。基线比率 1.92（9,229/4,794），预期 7 天内收敛 **<1.2**，同流量 30 天约减少 3,400+ 次子请求 |
| **CPU 时间** | **下降** | 最坏情况从"跑满 30s"收敛到各出站调用 ≤10s；免第三方 DNS 解析。`exceededResources`（10 次/30d）根因消除 |
| **KV 读** | +0（读取层未动） | M2-P1（内存缓存）尚未实施；每请求读 KV 模式不变 |
| **KV 写** | **一次性 +3** | KV 绑定激活后首次功能访问初始化 `config.json`/`tg.json`/`cf.json`；后台主动操作按需写 |
| **D1 / R2** | +0 | 未涉及 |
| **错误数** | **大幅负增量** | 362 → 预期 <50/30d（目标 <1%）；scriptThrewException 与 exceededResources 根因消除 |

**结论：无正增量成本。** 计费请求数不变，CPU 与子请求为主要负向变化。usage-monitor 的 80% 用量告警线不会因本次改动产生感知；反而在"告警原因"维度会看到 Workers 错误率下降。

## 四、风控风险评估

**结论：本轮改动整体降低（而非增加）CF 对本项目的风控风险。** 逐项对照 CF 对 Workers 代理类项目的典型风控信号：

| CF 风控信号 | 本项目现状 | 改动影响 |
|---|---|---|
| 大规模通用代理流量（ToS 限制项：非 HTML 代理流量占比） | 个人低流量（日均 ~160 req），远低于阈值 | 无变化 |
| 依赖第三方动态域名 / 滥用聚集点 | 改造前默认出站依赖 `{colo}.SsSs.nEt` 社区域名（DNS TXT 池）——**这正是风控关注的形态** | **↓ 消除**：改用官方 IP 池，流量形态常规化 |
| 资源滥用（CPU 跑满 / 内存峰值触发平台保护） | 改造前 exceededResources 10 次/30d + loadShed 262 次/30d，本身就是平台已感知的滥用信号 | **↓ 大幅降低**：超时收敛 + 子请求减少 + 错误率 7.55%→<1%（高错误率本身就是异常画像） |
| 重复模式化出站（扫描行为特征） | 官方直连池 10 个固定 IP | **中性**：Worker→CF 边缘连接是网络内部路径，非跨网扫描，无风控含义 |
| 平台功能使用 | Observability 开启、KV 正常使用 | **中性**：均为官方正常功能 |

**唯一需要长期留意的**：真正决定风控风险的是**流量形态本身**（代理流量占比、目标站点分布、并发模式、是否被举报），这些由使用方式决定。本轮改动没有放大它们——反而通过消除错误信号让流量画像更健康。7.55% 的错误率（loadShed + 异常）在平台视角本来就是"需要关照的 Worker"画像，降到 <1% 后画像改善。

**诚实声明不确定性**：CF 风控细则不公开，以上基于公开 ToS、平台机制（loadShed/exceededResources 即平台侧信号）与社区项目长期公开运行的观察推断，非官方保证。
