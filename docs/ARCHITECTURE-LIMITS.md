## H1 请求级配置的全局变量 sticky 泄漏 —— ✅ 已修复（2026-09-07，commit 本次优化）

**证据**（`src/config.js` L291-295，`全局读取配置` 内）：

```js
调试日志打印 = ['1', 'true'].includes(env.DEBUG) || 调试日志打印;
预加载竞速拨号 = ['1', 'true'].includes(env.PRELOAD_RACE_DIAL) || 预加载竞速拨号;
反代并发拨号数 = Math.max(1, Number(env.PROXY_CONCURRENT_DIAL) || 反代并发拨号数);
TCP并发拨号数 = Math.max(1, Number(env.TCP_CONCURRENT_DIAL) || TCP并发拨号数);
```

**为什么是硬伤**：Workers 的同一个 isolate 会**并发处理多个请求**，这些模块级变量是跨请求共享的：
- `|| 调试日志打印` 使 DEBUG **一旦开启就永久 true**（isolate 存活期内），请求 A 开 DEBUG 后，请求 B/C 的 `console.log` 全部泄漏输出（含路径、IP 等），且无任何机制回退；
- `预加载竞速拨号` 同理 sticky；
- `并发拨号数` 的 `|| 旧值` 回退语义：请求 A 配置了 4 路后，未配置的请求 B 会**继承 4** 而非回到默认 1——行为随请求顺序漂移。

**影响面**：信息泄露（日志）、性能行为不可预测、测试不可复现（test-config.js 每次手动重置全局正是这个问题的补丁式自白）。

**修复路径**：改为 per-request 上下文对象——`全局读取配置` 返回值已含大部分字段，把上述 4 个全局改为返回对象字段，`log()` 改收上下文参数。**改签名会波及所有 `log()` 调用点（约 130+ 处），是这次清单中唯一需要系统性重构的项**。折中方案：保留全局变量但每请求入口先**无条件重置**为 env 派生值（去掉 `|| 旧值`），一行修复 sticky，重构后置。
**成本**：折中修复 = 低（1 处改动 + 测试）；彻底重构 = 中高（跨模块签名变更）。

> **状态（2026-09-07）**：折中修复已落地——每请求无条件按 env 重置，sticky 消除；per-request 上下文重构保留为后续可选项。

## H2 核心数据面零自动化测试 —— 迭代安全网缺失

**证据**：
```
测试覆盖:  test-config.js(配置层) + test-subscribe.js(订阅层) ✅
零覆盖:    src/protocol/ 1,843 行(ws/vless/trojan/ss/grpc/xhttp)
           src/transport/ 2,469 行(forward/dial/grain/proxy/tls-client)
```

**为什么是硬伤**：协议帧解析与出站传输是**复杂度最高、出错代价最大**的代码（今天 M2-P0 的官方直连、M1-P1 的热补丁 bug 全部发生在边界层），但它们只能"部署后线上探测"验证。每次传输层改动的回归风险完全由人工 smoke 承担——这不是流程问题，是**无法在部署前发现协议级回归**的结构缺陷。

**为什么一直没补**：协议测试需要 mock TCP socket / WebSocketPair / DoH / KV——`test-config.js` 的 bundle-transform 模式可以复用，但 mock 层工程量约 2-3 天。

**修复路径**（分两步）：
1. 先做**纯函数层**：VLESS/Trojan/SS 帧解析函数（输入字节 → 输出目标+载荷）不需要 mock 网络，golden 字节样本即可覆盖，1 天工作量，收益最大；
2. 再做 `forwardataTCP` 的连接选择逻辑（mock `创建请求TCP连接器`），验证竞速/兜底/官方直连分支组合。
**成本**：中。这是 M2-P1 之后最值得投入的工程项——它决定了后续所有传输层改动（含 M2-P2）的安全性。

## H3 自实现 TLS 协议栈 —— 密码学自实现风险

**证据**：`src/transport/tls-client.js` 676 行，手写 TLS 1.2/1.3 客户端（含 X25519 密钥交换、ChaCha20-Poly1305/AES-GCM、证书解析、Finished 校验）。使用范围：`dial.js:144`（HTTPS 链式代理出站）、`main.js:275`（admin 代理检测）。

**为什么是硬伤**：手写密码学协议是安全工程的大忌——实现缺陷（ nonce 复用、填充错误、校验绕过）不会报错，只会静默降低安全性，且极难审计。TLS 栈的成熟实现（BoringSSL 等）经过数十年的漏洞打磨。

**缓解因素**（为什么排 H3 而非 H1）：**主流量不经过它**——WS+TLS 的加密由客户端与 CF 边缘完成，官方直连路径由 CF 网内代答；TlsClient 仅在"HTTPS 链式代理"这个可选功能里使用。攻击面 = 使用该功能的用户的出站段。

**修复路径**：无法在 Workers 内引入原生 TLS 库（平台限制），务实方案：
1. 短期：在 README/TROUBLESHOOTING 标注"HTTPS 链式代理的 TLS 为社区自实现，安全敏感场景请改用 SOCKS5/直连"；
2. 长期：跟随上游——若 cmliu 上游替换为经审计的实现（如 nugget/uh 的方案），手工移植。
**成本**：短期低（文档声明）；根本解决依赖上游生态。

## H4 单连接 16MB 上行缓冲 + 自研流合包的背压复杂度 —— ✅ 缓冲已下调（16MB→1MB，2026-09-07）

**证据**（`src/main.js:8`）：`上行队列最大字节 = 16 * 1024 * 1024, 上行队列最大条目 = 4096`；应用点 `ws.js:492`、`grain.js:284`。

**为什么是硬伤**：上行合包（小包聚合）是性能优化，但代价是**每连接最多缓冲 16MB**——Free 计划 isolate 内存 128MB，意味着理论并发安全线只有 ~8 个满缓冲连接。历史上 `exceededResources` 的 10 次记录正是这一层；M2-P0.5 的 fetch 超时只解决了出站侧，**流缓冲侧的背压未做任何改造**。合包逻辑本身（grain.js 590 行）是上游 2026-08 才引入的，8 月连修 3 个 bug（冲刷链/reader 取消/搬运 Promise 清理）——这是整个代码库公认最难写对的部分。

**影响面**：高并发大流量场景的 `exceededResources`；90% 额度（多用户）场景下的内存竞争。

**修复路径**：不推荐重写背压（风险极高）。务实做法：
1. 把 16MB 单连接上限**下调到 1-2MB**（上行合包目标只有 20KB，16MB 缓冲的收益存疑，纯下行透传不需要）——一行改动，显著提高并发安全线；
2. M2-P2 热路径优化时，参照 cfnew v2.9.8c 的实现对照移植，且必须在 H2 的传输层测试就位之后。
**成本**：缓冲下调 = 低（需观察对吞吐的影响）；背压重构 = 高（明确不建议）。

> **状态（2026-09-07）**：已下调至 1MB/2048 条，合包目标 20KB 不变；对正常流无感知（1MB ≈ 50 个合包周期）。

## H5 订阅转换外部单点（SUBAPI）——主流客户端可用性的单依赖

**证据**：`src/main.js` 订阅分支——clash/singbox/surge/loon/quanx 仍走 `SUBAPI.{特征码}ssss.net` 外部转换器；仅 shadowrocket/v2rayn 为零依赖直出。

**为什么是硬伤**：订阅是整个系统的**控制平面入口**——转换器故障 = 所有主流客户端拿不到/拿到错误配置（超时兜底只保证返回错误而非挂死）。cfnew v2.9.8c 已证明全格式可 Worker 内直出。

**修复路径**：M1-P1 直出样板（`生成节点链接文本` + 4 个直出函数）已就位，逐格式补齐内部生成器（clash 的 rule-providers、singbox 的 SRS 规则集是大头），最终删除 SUBAPI 分支。**成本**：中高（每格式 1-2 天 + golden 测试），适合拆成 5 个独立小迭代。

## H6 平台约束：CPU 10ms（Free 计划）—— 功能路线图的永久天花板

**证据**：Workers Limits 文档（Free: 10ms/请求）。非代码缺陷，但**决定功能边界**：

- ✅ 能做：流式透传（实测 ~1ms）、轻量配置解析、订阅文本生成
- ❌ 不能做：请求路径上的重计算——大量 JSON 转换、批量加密、图片处理、大规模列表生成
- **对路线图的具体约束**：M1-P1 订阅全内化时，Clash/SingBox 配置生成是纯文本拼装（可行），但**任何引入密码学运算的新协议（如 Reality）都要精算 CPU 预算**；usage-monitor 式的外部 API 调用必须保持 `ctx.waitUntil` 化。

**缓解**：唯一路径是升级 Workers Paid（$5/月，CPU 30s-5min）——已在合规文档的容量策略中列为 90% 额度场景的推荐项。

## 对照：审读中确认**健康**的设计（避免误伤）

| 设计 | 为什么是对的 |
|---|---|
| 代理路径零 KV 读（配置只在订阅/管理路径读） | 主流量无状态化，KV 额度不构成容量瓶颈 |
| 官方直连池 + 打乱 + 分批竞速 + 兜底回落（M2-P0） | 无外部依赖的多候选容错，`Promise.any` + 败者 socket 清理实现正确 |
| 直连 ↔ 反代互为兜底的双向回落链 | 任一路径故障自动切换，是错误率 7.55%→<1% 的结构基础 |
| per-connection 的 `remoteConnWrapper` 世代机制（generation + downlinkDrain） | 连接切换的竞态处理严谨，未发现代际错乱路径 |
| 构建/校验/测试三件套 + CI 防漂移（M0） | 双产物结构的漂移风险已被工具链覆盖 |
